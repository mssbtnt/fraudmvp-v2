  ---
  Comprehensive Codebase Feedback — Fraud MVP

  Overall Assessment

  A well-architected fraud intelligence MVP with a clear pipeline,
  Malaysian-market specificity, and production-ready patterns. The code is
  genuinely solid — the issues below are refinement-level, not structural
  failures.

  ---
  Strengths

  1. Architecture — Clean Pipeline Isolation
  The 5-stage pipeline (Collect → Extract → Score → Campaign → Alert) is cleanly
   separated via Redis queues. Each agent is independently runnable and can
  fail/restart without corrupting the pipeline. This is the right design for an
  MVP that needs to scale stages independently.

  2. Malaysian Market Deep Expertise
  The hardcoded bank codes (32 banks), mobile carrier prefixes, account length
  patterns, and phone risk classifications by country code are unusually
  thorough for an MVP. The alerter.py alone has ~200 lines of reference data
  that would take weeks to compile from scratch.

  3. Config-Driven Scoring
  All thresholds, weights, and keyword dictionaries live in YAML files
  (scoring_rules.yaml, keywords.yaml, sources.yaml). Changing scoring behavior
  doesn't require code changes — excellent for operational tuning.

  4. Demo Mode
  Every agent and scraper has a demo_mode flag that simulates data without
  credentials. This is essential for development and CI/CD without hammering
  real APIs.

  5. DB Auto-Migration Pattern
  Database._ensure_schema() using CREATE TABLE IF NOT EXISTS is idempotent and
  runs on every instantiation. This is a pragmatic, low-risk migration strategy
  for SQLite.

  6. Redis Queue Graceful Degradation
  QueueHandler catches redis.ConnectionError and falls back to no-op mode. The
  pipeline won't crash if Redis is temporarily unavailable — it just queues
  nothing.

  7. Cross-Type Deduplication
  The extractor has smart logic to detect when a phone number and bank account
  share the same digit string (e.g., "5019692019" as both phone and account),
  preventing false signal inflation.

  8. Queue LPUSH + RPOP (FIFO)
  Correct choice for a pipeline where ordering matters for temporal clustering.

  ---
  Issues & Risks

  Critical

  1. scorer.py:162 — Calls get_entity() method that doesn't exist on Database
  existing = self.db.get_entity(entity.value, entity.type)
  The Database class has get_entity_by_value() and get_recent_entities() but no
  get_entity(). This will raise AttributeError at runtime when draining the
  extracted_entities queue. It should be:
  existing = self.db.get_entity_by_value(entity.value, entity.type)

  2. collector.py:365 — discovered referenced before assignment
  discovered.append(ch_info)  # ← NameError: cannot access local 'discovered' 
  before assignment
  In snowball_pivot(), the variable discovered is used as a local list but is
  only assigned inside the try block. The outer discovered = [] on line 247 is
  in discover_telegram_channels(), not this method. Should initialize discovered
   = [] at the start of snowball_pivot.

  3. api/main.py — EntityResponse returns channels as a list, but list_entities 
  endpoint has an N+1 query problem
  for e in entities:
      edges = db.get_edges_for_entity(e["id"])   # ← 1 query per entity
      channels = list({edge["channel"] for edge in edges})
  At limit=500, this fires up to 500 individual queries per request. Should use
  a single batch query or a JOIN.

  High

  4. extractor.py:275 — add() is a closure that captures seen but seen.add(key) 
  happens after the early returns, risking duplicate entities if the function 
  returns early before reaching seen.add(key).
  The dedup check on line 277-293 adds to seen only at line 295 after the early
  returns. If two calls pass different types but same value and the first call
  returns early (e.g., wrong digit length), seen won't contain the key, and the
  second call could still pass the dedup check incorrectly.

  5. scorer.py — _drain_extracted_queue() deserializes each item then 
  immediately does a DB lookup by value+type, but the entity is already in DB 
  (upserted by extractor). This is two DB round-trips per entity instead of one.
  Better: the extractor already has the entity ID from upsert_entity — pass it
  in the queue message so scorer can skip the lookup.

  6. scorer.py:298-337 — cluster_entities() BFS clustering has O(n × k) behavior
   where k is average channel membership. With 10,000 entities this is fine, but
   the BFS re-visits the same channel_to_entities list repeatedly.
  No memoization of visited cluster IDs — the same entity can potentially be
  added to multiple campaigns if it shares channels with multiple separate
  clusters (though the visited set should prevent this, the algorithm is
  fragile).

  7. No transaction isolation around campaign upsert + entity tagging
  In database.py:upsert_campaign():
  conn.execute("INSERT INTO campaigns ...")
  conn.execute(f"UPDATE entities SET campaign_id=? WHERE id IN ({placeholders}) 
  ...")
  If the UPDATE fails, the campaign is already inserted. No rollback strategy.

  8. database.py:204 — ON CONFLICT ... WHERE excluded.last_seen > 
  entities.last_seen is a SQLite limitation issue
  The WHERE clause after ON CONFLICT DO UPDATE SET is valid in SQLite 3, but the
   lastrowid approach at line 208-212 after an ON CONFLICT upsert may not work
  correctly. The fetchone() on line 209-210 could fail if the conflict occurred
  and no row was actually updated.

  Medium

  9. database.py:275-286 — get_cross_channel_count() uses string interpolation 
  for datetime
  f"""
  SELECT ... WHERE timestamp >= datetime('{since}', '-{hours} hours')
  """
  This is safe for integers, but the {since} variable (an ISO timestamp string)
  is injected directly. If since contains a single quote, this breaks (and could
   be exploited if since ever came from user input). Should use parameterized
  queries.

  10. Missing indexes for scraped_messages.platform and scraped_messages.channel
  The schema only indexes text_hash. If you query SELECT * FROM scraped_messages
   WHERE platform=? AND channel=?, there's no index. With scale, this becomes a
  full table scan.

  11. QueueHandler singleton pool is module-level global (_pool), but is 
  recreated if QueueHandler() is instantiated with a different redis_url
  def _get_pool() -> redis.ConnectionPool:
      global _pool
      if _pool is None:
          _pool = redis.ConnectionPool.from_url(REDIS_URL, ...)
  If one instance uses redis://a:6379 and a second instance uses redis://b:6379,
   the second call still returns the pool for the first URL. This only matters
  if multiple Redis URLs are used, which isn't happening now — but it's a latent
   bug.

  12. llm_similarity.py:44-56 — Each _ollama_embed call creates a new 
  httpx.Client()
  No connection reuse. Should be a shared client or at least a connection pool.

  13. No pagination on get_recent_entities() result set in scorer.py
  entities = self.db.get_recent_entities(limit=10000)
  Always fetches up to 10,000 rows into memory. With 100+ campaigns, this loads
  all entities every run. Should consider date-range filtering.

  14. CORS wildcard
  allow_origins=["*"]  # ← Accepts requests from any origin
  Fine for MVP, but should be restricted in production.

  15. API token auto-generation in production
  if not API_ACCESS_TOKEN:
      API_ACCESS_TOKEN = secrets.token_urlsafe(32)
      logging.warning(...)
  Generates a new token on every startup if missing from .env. If the app
  restarts, all clients lose access until they read the new log output. Should
  fail fast instead.

  Low

  16. IBAN_RE is defined twice in extractor.py (lines 81 and 113)

  17. _to_dict() in collector.py is a fragile polyfill
  def _to_dict(obj):
      if isinstance(obj, dict): return obj
      if hasattr(obj, "__dict__"): return vars(obj)
      if hasattr(obj, "to_dict"): return obj.to_dict()
  The fallback vars(obj) won't work for dataclasses with __init__ arguments. The
   hasattr(obj, "to_dict") check is also a naming convention, not an interface —
   if a Telethon object has a to_dict method with different signature, it breaks
   silently.

  18. alerter.py is 400+ lines with no separation between formatting and 
  delivery
  Should be split into alert_formatter.py and alert_deliverer.py.

  19. No integration tests, no unit tests
  pytest is in requirements.txt but no tests/ directory exists. For a system
  handling fraud intelligence (which has false positive / false negative
  consequences), test coverage is important.

  20. Daily pipeline script (fraud-mvp-daily-pipeline.sh) is a shell script 
  calling sequential Python processes
  If step 3 fails, step 4 still runs. Consider a proper workflow orchestrator
  (e.g., just Python with proper error handling).

  Key Design Decisions

  - NDJSON parsing: OpenSanctions returns one JSON object per line, not a JSON
  array — fixed with split("\n") + per-line json.loads()
  - t.me domain filtering: t.me appears as a URL in records but is not a fraud
  domain — skipped
  - Clone entity flagging: records tagged "potential clone" are flagged with
  is_clone=True and surfaced in the message context
  - Separate OpensanctionsEntity dataclass: distinct from ScrapedEntity to
  preserve OpenSanctions-specific fields (record_id, is_clone,
  registration_number, telegram_channels)

  The entities are pushed to raw_messages queue as RawMessage objects with
  platform=opensanctions, ready for extraction by FraudExtractorAgent.
